## 5. Description
Grade Assignment Submission within an owned Course. The Actor-System interaction below describes implemented behavior; unimplemented extensions remain in section18.

## 6. Trigger
Teacher chooses the corresponding action in Teacher submission detail editor.

## 7. Preconditions
- PRE-1: Teacher is signed in, active, email verified and not suspended from teaching.
- PRE-2: The selected Course and required parent resources exist and are not deleted.
- PRE-3: Teacher owns the Course; content changes additionally require an editable Course status.
- PRE-4: An existing submitted Assignment answer is selected; numerical grading requires an explicitly configured scale.

## 8. Postconditions
**Success:** One authoritative submission stores score/maxScore, result status, grader, time and incremented revision. Gradebook has no independent copy.

**Failure:** No unauthorized data is exposed or updated. Validation/conflict failures preserve existing records. Technical multi-step failure recovery/limits are described in sections11 and15; full cross-collection transactions are not implied.

## 9. Normal Flow
1. Teacher opens an existing submission and reviews its answer.
2. System authenticates the Teacher and verifies submission, Assignment and Course ownership.
3. Teacher enters a numerical score and optionally feedback, then selects Save Grade and Feedback.
4. System validates the scale and revision and atomically locks the Assignment scale against concurrent changes.
5. System updates the current submission using a conditional revision check and records grader and grading time.
6. System recalculates learning progress from the updated result.
7. System confirms the result; Gradebook reads the same submission and the student can view it immediately.

## 10. Alternative Flows
AF1.NF3: A legacy Assignment has no numerical scale. Teacher explicitly chooses Passed or Needs Revision; system stores the legacy decision without inventing a numeric score, then continue NF5.
AF2.NF3: An already graded submission is edited. System replaces the current result and grading metadata with the same revision guard; continue NF4.

## 11. Exceptions
EX0.NF2: Authentication, teaching permission or ownership fails. System returns401/403 (or404 for unavailable parent resources), exposes no protected result, and ends the use case.

EX1.NF4: Missing scale or invalid/out-of-range score: reject, preserve the grade, return NF3.
EX2.NF5: Submission was resubmitted/edited concurrently: return conflict, preserve the newer result; Teacher must reload at NF1.
EX3.NF4: Assessment scale changed concurrently: reject and reload NF1.

## 13. Input/Data Validation
score: finite JSON number, 0 <= score <= Assignment.maxScore. maxScore explicitly configured >0 and <=1000000. passingScore optional, within the same scale. revision: nonnegative integer; UI always sends it. feedback optional string <=10000 chars. Numeric passing status is derived; client cannot also send passed.

## 14. Priority and Frequency of Use
Priority: High (Proposed planning value). Frequency: As needed during Course preparation, assessment or review; actual usage frequency is not measured.

## 15. Other Information and Assumptions
No numeric scale/pass threshold is guessed. With no Assignment passingScore, numeric status is graded and progress does not infer a pass. Historical grade audit/version history is not added; scale locks may remain after a failed grade write and can be retried using the same scale.

## 16. Acceptance Criteria
- AC-1: Normal flow yields the stated success postcondition with persisted/source-aligned values.
- AC-2: A different Teacher and an unauthenticated user cannot perform the protected action.
- AC-3: Each validation and alternate flow above preserves the documented zero/null, relation, time or revision distinction.
- AC-4: UI exposes loading/busy, empty where applicable, and error states without claiming success on failure.
- AC-5: Repeated reads/calculation do not create duplicate grades; writes follow their documented update semantics.
