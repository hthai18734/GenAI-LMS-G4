## 5. Description
View Assignment Submissions within an owned Course. The Actor-System interaction below describes implemented behavior; unimplemented extensions remain in section18.

## 6. Trigger
Teacher chooses the corresponding action in TeacherAssignmentSubmissionsPage.

## 7. Preconditions
- PRE-1: Teacher is signed in, active, email verified and not suspended from teaching.
- PRE-2: The selected Course and required parent resources exist and are not deleted.
- PRE-3: Teacher owns the Course; content changes additionally require an editable Course status.
- PRE-4: Actor supplies the required inputs listed in section13.

## 8. Postconditions
**Success:** Teacher sees only submissions belonging to an owned Assignment. Viewing does not modify submission state.

**Failure:** No unauthorized data is exposed or updated. Validation/conflict failures preserve existing records. Technical multi-step failure recovery/limits are described in sections11 and15; full cross-collection transactions are not implied.

## 9. Normal Flow
1. Teacher opens Submissions for an Assignment.
2. System authenticates the Teacher and verifies Course ownership.
3. Teacher selects a status filter and page.
4. System returns a bounded page of submissions with student identity, status, score and submission time.
5. Teacher selects View / Grade for a row.
6. System verifies ownership again and displays its answer, feedback, grading metadata and revision.

## 10. Alternative Flows
AF1.NF4: No matching submissions: show an empty state and pagination total zero; end.
AF2.NF3: Teacher changes page/filter: cancel obsolete list requests and continue NF4.

## 11. Exceptions
EX0.NF2: Authentication, teaching permission or ownership fails. System returns401/403 (or404 for unavailable parent resources), exposes no protected result, and ends the use case.

EX1.NF3: Invalid page, limit, status or student ID filter: reject with validation response; return NF3.
EX2.NF6: Submission or active Assignment no longer exists: show not-found and end detail loading.

## 12. Business Rules
I3-HUY-R01. Definitions and approval status are in [README](README.md#rule-identifiers-and-review-status). Local IDs are not claimed to be official RDS identifiers.

## 13. Input/Data Validation
page: integer 1-1000000; limit: integer 1-100, default20. status: submitted/graded/passed/needs_revision. Optional API studentId: valid ObjectId. List excludes answer; detail includes it. Detail may include a private PDF/DOC/DOCX attachment (one file,25 MiB). Teacher previews PDF or downloads Word through the authenticated attachment endpoint.

## 14. Priority and Frequency of Use
Priority: High (Proposed planning value). Frequency: As needed during Course preparation, assessment or review; actual usage frequency is not measured.

## 15. Other Information and Assumptions
UI provides status filter; studentId filter is available through API. Submission attachments are supported; only the submitting Student and Course owner Teacher/admin may access them. See COMPLETION_UPDATE.md.

## 16. Acceptance Criteria

- AC-2: A different Teacher and an unauthenticated user cannot perform the protected action.
